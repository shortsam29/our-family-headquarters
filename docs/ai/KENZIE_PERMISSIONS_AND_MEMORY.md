# Kenzie Permissions and Memory

## Current permissions

Kenzie may explain, suggest, organize, recommend, and draft. She cannot create, edit, delete, send, announce, schedule, complete, or otherwise modify the app. She must label proposals as unsaved and may never claim success without a future verified tool result.

Actions are typed as informational, suggestion, draft, confirmation-required, or prohibited.

## Current memory

The checked-in family profile remains separate from private learned memory. After a one-time disclosure, the protected server memory service may save direct, high-confidence, low-sensitivity statements in an allowlisted category. Complete conversations are never stored. Temporary project context expires automatically; durable preferences remain until the owner edits or deletes them.

Each memory belongs to a household UUID and recipient family-member UUID. RLS grants only that authenticated owner access; a manager role does not create blanket access. Members can review, edit, delete, delete all, pause, resume, opt out for one message, or pause memory for a conversation. Retrieved memory is compact, relevance-filtered, and labeled as untrusted data before prompt assembly.

Sensitive health, financial, credential, precise-address, abuse, sexual, accusation, and prompt-injection content is rejected. Child accounts use the same owner-only boundary plus a narrower accepted-category allowlist. No parent visibility is added without a future verified guardianship and product-consent design.

## Future providers (disabled)

Provider-independent interfaces describe read-only internal/Google/Apple/Microsoft calendar access, proposed calendar actions, explicit user confirmation, idempotency keys, duplicate detection, time-zone-aware scheduling, proposed push notifications, confirmed notification sending, and action audit records. No external calendar or notification provider is connected and no execution implementation exists.
